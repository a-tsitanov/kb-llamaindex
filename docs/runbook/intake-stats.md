# Intake stats — сверка «залито против принято»

## Что отвечает

`GET /api/v1/intake/stats` — одна выдача на вопрос «почему документов в
графе меньше, чем мы залили». Срез графовый: граф выбирается как у любой
ручки — заголовком `X-Graph`, иначе единственным графом ключа, иначе
`default`. Право — `read`.

```
curl -s -H "X-API-Key: $KEY" "http://localhost:8000/api/v1/intake/stats" | jq
```

Параметры: `stuck_after_minutes` (1..10080, по умолчанию 120) — порог
застревания; `limit` (1..100, по умолчанию 10) — длина списков в ответе.

## Лестница сверки

Главное в ответе — три корзины, которые НЕ складываются в одно число:

```
rows = documents + versions + sightings
```

| Поле | Что это |
|---|---|
| `rows` | строк в реестре приёма — «сколько раз что-то залили» |
| `documents` | из них принятых документов, канонических |
| `versions` | `{статус: сколько}` вторых комплектов того же тела — политика `on_duplicate=version` |
| `sightings` | наблюдений перепоста: тело уже принято, у строки нет и не будет обработки |
| `by_status` | эффективный статус принятых, нули включены; отклонённый приёмом виден как `skipped` |
| `duplicate_share` | `(versions + sightings) / rows` |

Разница `rows − documents` — это повторы, а `by_status.skipped` — отказы
приёма. Вместе они и объясняют, почему в графе меньше: остальное либо ещё
в очереди (`pending`/`processing`), либо упало (`failed`).

Дальше:

| Поле | Что это |
|---|---|
| `throughput` | `arrived_1h/24h` по времени записи строки, `finished_1h/24h` по терминальным статусам обработки |
| `stuck` | `pending` и `processing` без движения дольше порога; `threshold_minutes` — применённый порог |
| `coverage` | `earliest_doc_date` / `latest_doc_date` / `without_doc_date` — какой период покрыт датами документов |
| `recent_errors` | последние падения пайплайна с текстом ошибки |
| `top_reject_reasons` | вердикты классификатора агрегатом — чего отсекли больше всего |
| `top_doc_types` | типы принятых документов |

`finished_*` считает и версии: они идут в пайплайн наравне с документами,
и работа по ним — настоящая.

## Чем отличается от соседних поверхностей

| Поверхность | Срез | Когда она |
|---|---|---|
| `GET /intake/stats` | весь граф, включая строки без канала | нужна сверка приёма и обработки |
| `GET /stats/messages` | по каналам и группам, строки с пустым каналом отброшены | нужны числа по каналу (`docs/runbook/message-stats.md`) |
| `python -m scripts.check_ingestion` | весь граф, прямо из Postgres, без API и ключа | API недоступен или нужна диагностика на стенде |

Поэтому `documents` здесь и сумма `total` в `/stats/messages` совпадают
только там, где у всех документов заполнен канал. Это не расхождение, а
разные вопросы.

## Чего в ответе нет

Очереди RabbitMQ: `ready`/`unacked` живут в брокере, API к нему за этим не
ходит. Смотреть `rabbitmqctl list_queues` или UI брокера — см.
`docs/DEPLOYMENT.md`.
