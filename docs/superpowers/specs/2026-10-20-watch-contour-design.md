# Контур наблюдения (P2): одна дуга, доставка, провенанс — спека

Дата: 2026-10-20.
Статус: решения приняты пользователем 2026-10-20, объём зафиксирован.
Карта: `docs/superpowers/plans/2026-10-17-project-boundaries.md` §5.
Предшественники: `2026-10-15-entity-watch-design.md` (подписки и журналы),
`2026-10-19-intake-contour-design.md` (приём, источник, дубль).

## 1. Зачем

Наблюдение за сущностями работает, но существует в ДВУХ параллельных
экземплярах, и это главный факт, определяющий объём.

| Дуга | Подписка | Детекторы | Доставка |
|---|---|---|---|
| `:Alert` в Nebula (Arc 2) | флаг `Entity.watched` | `detect_alerts`: `new_connection`, `risk_rise`, `burst` | один глобальный webhook `MONITOR_WEBHOOK_URL`, прав не проверяет |
| `watch_event` в Postgres | таблица `watch` (`owner`, `kinds`, `muted_until`) | `run_watch_sweep`: `new_mention`, `new_connection`, `new_identifier`, `new_event`, `contradiction` | **нет вовсе** — только pull через MCP `kb_watch_feed` |

`new_connection` порождают обе, то есть критерий карты контуров
«подписка даёт одно уведомление на событие» при двух дугах недостижим в
принципе. Остальные дыры: у событий нет провенанса приёма (хотя после P1
он есть в реестре), доставка не проверяет прав, а `new_mention` шумит на
каждый документ.

## 2. Решения

Приняты пользователем 2026-10-20.

| Решение | Выбор |
|---|---|
| Модель подписок | ОДНА: Postgres `watch` / `watch_event`. Дуга `:Alert` выводится из эксплуатации целиком |
| `risk_rise` | переселяется в `watch_event` как вид события (чтение `Entity.risk_score`/`risk_score_prev` остаётся, запись `:Alert` уходит) |
| `burst` | НЕ восстанавливается: под nebula он не портирован вовсе и выключен по умолчанию. Уходит в бэклог явной записью |
| Канал доставки | webhook НА ПОДПИСКУ (URL в строке `watch`), а не один глобальный из env |
| Telegram | не делаем (свой бот удалён в P0; исходящие уведомления покрывает webhook) |
| Шум `new_mention` | потолок пушей в сутки на подписку, остаток — одной сводкой (дайджест как форма тела, а не отдельный канал) |

## 3. Границы контура

Пакет `src/watch/`:

| Модуль | Откуда | Отвечает за |
|---|---|---|
| `src/watch/journal.py` | `src/graph/watch_journal.py` | запись журналов на ингесте |
| `src/watch/sweep.py` | `src/workflow/monitor/watch_sweep.py` | детекторы: строки журналов → события |
| `src/watch/repository.py` | `src/storage/watch.py` | SQL по `watch`, `watch_event`, `watch_seen`, журналам, курсорам, доставке |
| `src/watch/delivery.py` | `src/workflow/monitor/delivery.py` | отправка, ретраи, дедуп доставки, потолок и дайджест |
| `src/watch/activities.py` | `src/workflow/monitor/activities.py` | Temporal-активности свипа и доставки |
| `src/watch/workflow.py` | `src/workflow/monitor/workflow.py` | `MonitorSweepWorkflow` (имя класса НЕ меняется) |

Имена классов воркфлоу и активностей сохраняются: по ним работает
Temporal-расписание (`scripts/setup_monitor_schedule.py`), и переименование
означало бы ручную пересборку расписания на каждом стенде.

Правила границы (исполняются arch-тестом):

* ядро (`src/graph`, `src/retrieval`, `src/workflow`) не импортирует
  `src.watch`, кроме ОДНОГО объявленного адаптера — записи журналов из
  `src/workflow/activities/build_property_graph.py`;
* `src/watch` не импортирует `src.intake`, кроме ОДНОГО объявленного
  чтения — `IntakeRepository.provenance_of` (§5);
* SQL по `documents` остаётся в приёме: наблюдение спрашивает провенанс
  методом, а не своим запросом.

## 4. Вывод дуги `:Alert`

Удаляется: `detect_alerts`, `deliver_alerts`, `src/graph/alerts.py`,
`src/graph/alert_store.py`, флаг `Entity.watched` (запись и чтение),
настройки `MONITOR_WEBHOOK_URL` / `MONITOR_WEBHOOK_TIMEOUT_S` /
`MONITOR_RISK_RISE_DELTA` переезжают в раздел наблюдения, burst-настройки
уходят вместе с детектором.

Что НЕ удаляется: `MONITOR_ENABLED`, очередь, расписание, интервал свипа —
свип остаётся, он теперь делает только журнальную работу.

`risk_rise` как вид события: детектор читает у наблюдаемых сущностей
`risk_score` и `risk_score_prev`, и при росте не меньше
`risk_rise_delta` пишет `watch_event` с `dedup_key =
risk_rise:<vid>:<score, 2 знака>`. Округление в ключе — это и есть
политика повтора: дальнейший рост даёт новое событие, та же величина —
нет. `risk_snapshot` остаётся неиспользованной таблицей (она не нужна,
пока предыдущее значение лежит на узле графа) и в объём не входит.

## 5. Провенанс в теле события

После P1 реестр приёма знает про документ то, чего не знает граф:
источник (`source_kind`, шаг 1.4A), вердикт приёма и ссылку на владельца
тела (`intake_status`, `duplicate_of`, шаг 1.2).

Событию это нужно, потому что «новая связь» из перепоста и «новая связь»
из первоисточника — разной ценности, а подписчик по текущему телу
события их не различает.

Решение: приём получает узкое чтение

```python
async def provenance_of(self, doc_ids: list[uuid.UUID]) -> dict[str, dict]
# {str(doc_id): {"source_kind", "intake_status", "duplicate_of", "doc_date"}}
```

Свип зовёт его ОДИН раз на пачку событий и кладёт результат в
`watch_event.detail` под ключом `provenance`. Поля `detail` уже
`JSONB`, миграции не требуется, старые события просто без ключа.

Почему методом, а не join'ом: SQL по `documents` принадлежит приёму
(критерий шага 1.3), и второй его экземпляр в наблюдении разъехался бы с
первым при следующей правке реестра — ровно так разъехались читатели
статуса до расщепления.

## 6. Доставка

### 6.1 Адресат

Колонка `watch.webhook_url TEXT NOT NULL DEFAULT ''` — пусто значит «не
доставлять, только лента». Глобального адресата больше нет: один URL на
установку не может быть правильным для нескольких подписчиков, и именно
он делал доставку безадресной.

### 6.2 Журнал доставки

```sql
CREATE TABLE IF NOT EXISTS watch_delivery (
    owner       TEXT   NOT NULL,
    event_id    BIGINT NOT NULL,
    state       TEXT   NOT NULL DEFAULT 'pending'
                CHECK (state IN ('pending','delivered','failed','suppressed')),
    attempts    INTEGER NOT NULL DEFAULT 0,
    last_error  TEXT   NOT NULL DEFAULT '',
    digest_of   BIGINT,
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (owner, event_id)
);
```

Первичный ключ `(owner, event_id)` И ЕСТЬ дедуп доставки: одно событие
одному подписчику уходит один раз, сколько бы раз свип ни перезапускался.
`suppressed` — не влезло в суточный потолок и ушло в сводку; `digest_of`
— id сводной отправки, чтобы по строке было видно, где событие всё-таки
показали.

Состояние доставки живёт ОТДЕЛЬНО от `watch_seen` (прочтение
подписчиком): «отправлено» и «прочитано» — разные факты, и смешивать их
значило бы считать доставленным то, что человек открыл в ленте сам.

### 6.3 Потолок и дайджест

`watch.daily_push_limit INTEGER` (NULL = берётся из настроек, умолчание
20). События пишутся ВСЕ — лента полная всегда. Пуши идут до потолка в
сутки на подписку; что не влезло, помечается `suppressed` и в конце
прохода уходит ОДНОЙ сводкой: количество по видам, первые N названий
сущностей, окно времени. Сводка тоже регистрируется в `watch_delivery`
(собственной строкой с `event_id = 0`, остальные ссылаются на неё через
`digest_of`).

Порог значимости не вводится: угадывать «важность» события нечем, а
потолок с дайджестом решает ту же задачу, ничего не теряя.

### 6.4 Право на граф при КАЖДОЙ доставке

Доставка — точка утечки: URL назначает владелец подписки, а тело несёт
имена сущностей графа. Поэтому перед каждой отправкой проверяется, что у
владельца подписки ЕСТЬ живой ключ, которому разрешено читать этот граф:

```python
records_for_owner(owner) -> list[ApiKeyRecord]   # новое, src/tenancy/api_keys.py
authz.guard(record, graph.id, graph.tenant_id, Action.READ)
```

Ни одного проходящего ключа — доставка не идёт, строка остаётся
`pending`, подписка логируется один раз за проход. Это и есть «отзыв
прав останавливает доставку»: физическая изоляция таблиц от утечки через
webhook не спасает, потому что утечка идёт наружу.

При создании подписки право проверяется там, где она создаётся (MCP
`kb_watch` уже ходит через шов `src/mcp/_shared.py`), — здесь ничего
нового.

## 7. Что проверяется

| Критерий карты | Как проверяется |
|---|---|
| одно уведомление на событие, а не на документ | дуга одна; `(owner, event_id)` в `watch_delivery`; `new_mention` сверх потолка — в сводке |
| в уведомлении видно, откуда оно | `detail.provenance` с источником, вердиктом приёма и ссылкой на владельца тела |
| отзыв прав останавливает доставку | `records_for_owner` + `authz.guard` перед каждой отправкой |
| границы контура | arch-тест: ядро не импортирует `src.watch` (кроме адаптера журналов), наблюдение не импортирует приём (кроме `provenance_of`) |

## 8. Вне объёма

Telegram и прочие каналы; порог значимости; `burst` (не портирован под
nebula, выключен); `risk_snapshot`; ретраи с отдельной очередью (хватает
счётчика попыток в строке и следующего прохода свипа); удаление
`documents.status`; подписка на группу сущностей вместо одной.
