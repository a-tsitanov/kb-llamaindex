# Контур приёма (intake): дедуп, расщепление реестра, границы пакета

Дата: 2026-10-19. Статус: утверждён в брейншторме, ожидает ревью спеки.
Связано: [`2026-10-17-project-boundaries.md`](../plans/2026-10-17-project-boundaries.md) §4
(шаги 1.1–1.3), [`2026-10-18-tenancy-authz-design.md`](2026-10-18-tenancy-authz-design.md)
(арендаторы и права; этот контур наследует `GraphContext` и действия как есть).

## Задача

Ядро — графовый движок «документ → граф». Всё, что происходит **до** него —
контроль входной группы, отсев мусора, хранение оригиналов, решение «брать ли
этот документ» — сегодня размазано по маршрутам API, хранилищу ядра и
воркфлоу. Контур приёма выделяется в собственный пакет и получает то, чего у
него нет вовсе: **проверку на повтор по содержимому**.

Три факта, с которых всё начинается (проверено 2026-10-19 на
`a-tsitanov/tenancy-authz`):

- `src/api/routes/ingest.py:139` — `doc_id = uuid.uuid4()`. Контентного дедупа
  нет. Единственная проверка на дубль — `WorkflowAlreadyStartedError` → 409, но
  workflow-id строится из свежего UUID, поэтому **не срабатывает никогда**. Один
  и тот же файл, залитый дважды, проходит пайплайн дважды, порождает второй
  комплект сущностей и лишние пары для ER-судьи.
- Домен статуса смешивает два контура:
  `pending | processing | completed | vector_only | failed | skipped`.
  `pending` и `skipped` — решения приёма, остальное — ход обработки.
- Классификатор (`src/ingestion/classifier.py`) решает, брать ли документ, но
  живёт внутри ingest-воркфлоу и пишет свой вердикт как `status='skipped'`,
  то есть как состояние обработки.

Критерий успеха: повторная заливка того же файла в тот же граф не доходит до
хранилища и не порождает работы; ядро не содержит кода, отвечающего на вопрос
«брать ли этот документ»; тот же файл в другом графе — новый документ.

## Решения

| # | Решение |
|---|---|
| I1 | Контур приёма владеет реестром входящих целиком: хеш, оригиналы, источник, вердикт приёма, статус приёма. Ядро ведёт только статус обработки. |
| I2 | Дедуп **точный**, по sha256 тела. Нечёткий («тот же документ в другом формате») — вне объёма. |
| I3 | Уникальность хеша — в пределах графа. Отдельной колонки для этого не нужно: `documents` живёт в схеме графа. |
| I4 | Политика повтора выбирается параметром `on_duplicate`: `reject` (умолчание), `version`, `replace`. |
| I5 | Хеш считается **до** записи в MinIO. |
| I6 | Классификатор переезжает в контур приёма, но по-прежнему исполняется воркером: LLM-гейт нельзя держать синхронно в HTTP-запросе. Делим владение, не процесс. |
| I7 | Публичные пути маршрутов не меняются (`POST /api/v1/ingest`, `GET /api/v1/ingest/{job_id}`, `GET /api/v1/documents/{doc_id}`). Переезжает код, не контракт. |
| I8 | `documents.status` сохраняется в схеме, но перестаёт записываться; удаляется отдельным шагом после того, как все читатели переведены и выкат устоялся. |

## 1. Схема

Правки идут в `src/storage/pg_schema.py` (`GRAPH_DDL`) — эти таблицы живут в
схеме графа, не в `public`.

### 1.1 `documents` получает колонки приёма

```sql
ALTER TABLE documents ADD COLUMN IF NOT EXISTS content_sha256 TEXT;
ALTER TABLE documents ADD COLUMN IF NOT EXISTS intake_status  TEXT NOT NULL DEFAULT 'accepted';
ALTER TABLE documents ADD COLUMN IF NOT EXISTS intake_reason  TEXT NOT NULL DEFAULT '';
ALTER TABLE documents ADD COLUMN IF NOT EXISTS duplicate_of   UUID REFERENCES documents(id);
ALTER TABLE documents ADD COLUMN IF NOT EXISTS source_kind    TEXT NOT NULL DEFAULT 'upload';

ALTER TABLE documents DROP CONSTRAINT IF EXISTS documents_intake_status_check;
ALTER TABLE documents ADD CONSTRAINT documents_intake_status_check
    CHECK (intake_status IN ('accepted', 'duplicate', 'rejected'));

CREATE UNIQUE INDEX IF NOT EXISTS documents_sha_idx
    ON documents (content_sha256) WHERE content_sha256 IS NOT NULL;
CREATE INDEX IF NOT EXISTS documents_intake_status_idx ON documents (intake_status);
```

Частичный индекс — чтобы существующие строки без хеша не конфликтовали друг с
другом.

**Почему индекс не в `public`.** Таблица лежит в схеме графа, поэтому
уникальность автоматически действует в пределах графа. Глобальный индекс был бы
утечкой между арендаторами: отказ по дублю раскрывает, что такой документ уже
есть у соседа, а хеш проверяется подбором.

### 1.2 `doc_processing` — новая таблица, владелец ядро

```sql
CREATE TABLE IF NOT EXISTS doc_processing (
    doc_id     UUID PRIMARY KEY REFERENCES documents(id) ON DELETE CASCADE,
    status     TEXT NOT NULL DEFAULT 'pending'
               CHECK (status IN ('pending','processing','completed','vector_only','failed')),
    error      TEXT NOT NULL DEFAULT '',
    summary    TEXT NOT NULL DEFAULT '',
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX IF NOT EXISTS doc_processing_status_idx ON doc_processing (status);
```

`skipped` из домена ядра исчезает: отказ классификатора — это
`documents.intake_status='rejected'`.

Список таблиц для проверки готовности графа выводится регуляркой из `GRAPH_DDL`
(`pg_schema.graph_tables()`), поэтому новая таблица попадает туда сама и
отдельного списка править не нужно. Это проверяется тестом.

### 1.3 Перенос существующих строк

Одноразовый шаг под именем `intake_split_v1` в `public.schema_migration`
(механика заведена спекой арендаторов), выполняется для **каждой** схемы графа
внутри `migrate_graph_schema`:

```sql
INSERT INTO doc_processing (doc_id, status, error, summary, updated_at)
SELECT id,
       CASE WHEN status = 'skipped' THEN 'pending' ELSE status END,
       error, summary, updated_at
  FROM documents
 WHERE status <> 'skipped'
ON CONFLICT (doc_id) DO NOTHING;

UPDATE documents
   SET intake_status = 'rejected',
       intake_reason = COALESCE(NULLIF(error, ''), 'classifier (pre-split)')
 WHERE status = 'skipped';
```

`intake_reason` берётся из `documents.error`, а литерал — только фолбэк для
строк с пустым `error`: до расщепления причину отказа писал в `documents.error`
`mark_skipped`, строки обработки у отклонённого документа нет, и голый литерал
навсегда затёр бы причину в ответе API (там и `error`, и `intake_reason`
считаются выражением `eff_error`, которое у такого документа вырождается в
`intake_reason`).

Пропущенные классификатором документы не получают строку обработки — обработки у
них не было. Хеша у исторических строк нет и не будет: пересчитывать его значит
скачать из MinIO весь корпус. Они просто не участвуют в дедупе, и это
зафиксировано как принятое ограничение.

### 1.4 Кто что пишет после расщепления

| Момент | `documents` | `doc_processing` |
|---|---|---|
| `POST /ingest`, документ принят | строка: хеш, пути, источник, `intake_status='accepted'` | строка со `status='pending'` |
| `POST /ingest`, точный дубль | ничего не пишется (при `reject`) | — |
| `fetch_source` начал | — | `processing` |
| классификатор отказал | `intake_status='rejected'`, `intake_reason` | строка **удаляется** |
| `finalize` | — | `completed` / `vector_only` |
| ошибка | — | `failed`, `error` |

Удаление строки обработки при отказе — осознанный выбор: иначе документ вечно
висит в `pending`, то есть таблица врёт. Причина отказа сохраняется на стороне
приёма.

## 2. Дедуп

### 2.1 Где считается

В `POST /ingest`, сразу после `contents = await file.read()` и **до**
`put_object`. Тело и так читается целиком в память, поэтому sha256 не добавляет
ни чтения, ни буфера. Считать после заливки бессмысленно: дубль уже съел диск.

### 2.2 Политика

Параметр формы `on_duplicate`, значения и поведение:

| Значение | Поведение |
|---|---|
| `reject` (умолчание) | 409, тело `{"message": "duplicate", "doc_id": "<id первого>", "intake_status": "<его статус>"}`. В MinIO ничего не пишется, в очередь ничего не кладётся. |
| `version` | Новая строка, `duplicate_of` = id первого, документ идёт в пайплайн. Осознанный переингест под новую версию модели или промпта. |
| `replace` | Новая строка, старая получает `intake_status='duplicate'` и `duplicate_of` = id новой; объекты старой в MinIO не удаляются. Для исправления битой заливки. |

Неизвестное значение — 422 до любой работы.

**`force` и `on_duplicate` ортогональны, смешивать их нельзя.** Существующий
`force=true` обходит **классификатор**
(`src/workflow/activities/classify_document.py:23` — «forced (rules bypassed)»),
а не проверку на повтор. Его смысл не меняется, противоречия между флагами не
существует, и отдельного 422 на их сочетание не нужно. Это разные вопросы:
«стоит ли этот документ обработки» и «не видели ли мы его уже».

Раскрытие `doc_id` первого документа в теле 409 безопасно: он в том же графе,
то есть у того же арендатора.

### 2.3 Чего дедуп не ловит

Один и тот же документ, пересохранённый в другом формате (docx → txt, PDF через
другой принтер), даёт другой хеш и пройдёт как новый. Это вне объёма (I2):
нечёткий дедуп — отдельная задача с собственной ценой ошибки (ложное склеивание
двух разных документов хуже, чем лишний проход).

## 3. Границы пакета

### 3.1 Что переезжает

| Откуда | Куда |
|---|---|
| `src/ingestion/classifier.py` | `src/intake/classifier.py` |
| `src/ingest_queue/{topology,publisher,consumer,priorities}.py` | `src/intake/queue/` |
| `src/api/routes/ingest.py` | `src/intake/api/ingest.py` |
| `src/api/routes/documents.py` | `src/intake/api/documents.py` |
| SQL по `documents` из `src/storage/postgres.py` | `src/intake/repository.py` |

В `src/storage/postgres.py` остаётся работа с `doc_processing`. Обращение к
`documents` из `src/workflow/graph_lifecycle/activities.py` (подсчёт при удалении
графа) переводится на репозиторий приёма.

Маршруты регистрируются в `src/api/main.py` по прежним путям (I7).

### 3.2 Правило импорта

Ядро (`src/graph`, `src/retrieval`, `src/workflow` за вычетом активности
классификатора) не импортирует `src.intake`. Контур приёма не импортирует
`src.graph`.

Проверяется arch-тестом, который разбирает импорты AST и падает со списком
нарушителей. Исключение ровно одно и оно явное: активность, вызывающая
классификатор, живёт в `src/workflow/activities/` и импортирует
`src.intake.classifier` — исполнение остаётся в воркере (I6).

### 3.3 Читатели статуса

Переводятся на `doc_processing` в том же изменении, иначе два источника истины
разойдутся:

- `AsyncPostgres.get` — отдаёт объединённую строку (приём + обработка);
- `status_counts_by`, `timeline_counts` — соединение двух таблиц; их зовут
  MCP-инструменты `tools_server.py:676` и `:700`;
- `chunk_repository.py:162` — читает `get`, меняется вместе с ним;
- `GET /ingest/{job_id}` — отвечает и о приёме, и об обработке; документ,
  отклонённый классификатором, перестаёт выглядеть «пропавшим».

## 4. Ответы маршрута приёма

| Ситуация | Код | Тело |
|---|---|---|
| Принят | 202 | `{"job_id": "<doc_id>"}` (как сейчас) |
| Точный дубль, `on_duplicate=reject` | 409 | `{"message":"duplicate","doc_id":…,"intake_status":…}` |
| Неизвестный `on_duplicate` | 422 | перечисление допустимых |
| Нет прав на запись | 403 | как в спеке арендаторов |
| Чужой или несуществующий граф | 404 | `graph not found` |

  остаться тем же.

## 6. Вне объёма

- Нечёткий дедуп (I2).
- Пересчёт хешей для исторических строк.
- Реестр источников и принципалы фидеров — шаг 1.4 карты.
- `GET /intake/stats` — шаг 1.5.
- Квоты и честность приёма между арендаторами — шаг 1.6, колонка
  `graphs.max_inflight` остаётся зарезервированной.
- Удаление `documents.status` (I8) — отдельный шаг после выката.
- Журнал выдач оригиналов и право `download_original` — уже сделано спекой
  арендаторов.

## 7. Риски

- **Два источника истины о статусе** на время перехода. Смягчение: все читатели
  переводятся в том же изменении, запись в `documents.status` прекращается, и
  это закрывается тестом-гардом.
- **Миграция строк идёт по каждой схеме графа.** На пустых графах бесплатна, на
  `default` — один `INSERT … SELECT` по таблице документов. Выполняется внутри
  `migrate_graph_schema`, то есть под тем же замком, что и остальной DDL.
- **Откат.** Новые колонки и таблица аддитивны; откат кода на предыдущий коммит
  работает, пока `documents.status` не удалён (I8) — но записи, сделанные новым
  кодом, в нём не отразятся.
- **`ON DELETE CASCADE`** у `doc_processing.doc_id` означает, что удаление
  документа уносит и его обработку. Это и требуется, но стоит помнить при
  ручных чистках.

## Поправка от 2026-10-19: наблюдение перепоста вместо второй копии

Решение пользователя по открытому вопросу «кросс-канальный дедуп»: **в графе
остаётся ровно одна копия тела**. Это закрывает оба варианта, которые
обсуждались раньше, — умолчание `on_duplicate=version` для фидеров и сужение
ключа дедупа до `(тело, канал)`: каждый из них создаёт второй комплект чанков и
узлов для того же текста.

Чтобы канал-получатель при этом не исчезал из отчётности, `reject` перестаёт
быть чистым отказом: при повторе **атрибутированного** тела приём пишет
*наблюдение* — одну строку `documents` с `intake_status='duplicate'`,
`duplicate_of` на владельца тела и **тем же** путём в MinIO (второго объекта не
появляется). Строки `doc_processing` у наблюдения нет, в очередь оно не уходит,
в граф не попадает. Ответ остаётся `409` с прежним телом.

Следствия, закреплённые тестами:

- `EFFECTIVE_STATUS` получает ветку `intake_status='duplicate' → 'duplicate'`:
  иначе наблюдение упало бы на `documents.status` с вечным `pending` (I8) и
  выглядело бы ждущим обработки.
- `status_counts_by`: наблюдение идёт в добавочное `versions` как
  `{"duplicate": N}`; `total` и разбивка по статусам не меняются.
- `timeline_counts`: предикат становится
  `(duplicate_of IS NULL OR intake_status = 'duplicate')` — версия не добавляет
  дню сообщения, наблюдение добавляет (иначе канал, живущий перепостами,
  показывал бы ноль).
- Неатрибутированный повтор (пустые `channel` и `group`) наблюдения **не**
  пишет: обе группировки отчётности идут по этим колонкам, а строк в
  `documents` прибавлялось бы на каждый повторный прогон документированных
  заливок.
- Под `version` наблюдение не пишется — там создаётся настоящий документ.
- Значение `duplicate` в CHECK колонки `intake_status` теперь ЗАНЯТО
  наблюдением, а не зарезервировано под отложенную политику `replace`. Если
  `replace` когда-нибудь появится, ей нужно собственное значение.
- `find_by_sha` возвращает `CanonicalDoc(id, intake_status, path)`: путь нужен,
  чтобы наблюдение ссылалось на канонический объект.

Исторические перепосты, отклонённые до этой поправки, восстановлению не
подлежат — следа от них не осталось.
