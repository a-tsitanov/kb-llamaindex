# Разделение контуров: ядро / intake / наблюдение / харнесс — план

Дата: 2026-10-17, обновлён 2026-10-18 под текущий main (`c3191cef`).
Статус: черновик, не утверждён.

Цель: ядро остаётся графовым движком «документ → граф». Приём документов (контроль
входной группы, дедуп, оригиналы) выделяется в контур **intake**, который владеет
реестром входящих. Наблюдение за сущностями получает собственные границы. Сверху
встаёт харнесс. Поверх всего — tenant и авторизация.

Принятые решения:

- Резать ради **порядка в коде** и **контракта для агента**, не ради переиспользования
  ядра и не ради независимого деплоя. Следствие: **новых репозиториев не заводим**,
  процессы не делим, пока не появится отдельная причина. Границы — пакетные, с явными
  интерфейсами.
- **Intake владеет реестром целиком**: хеш контента, оригиналы, источник, вердикт
  приёма, статус приёма. Ядро ведёт только статус обработки.

## 2. Авторизация: где проходит

Разделить два механизма, которые легко спутать:

- **Изоляция** — техническая невозможность дотянуться до чужих данных. Уже есть,
  держится на типах (`GraphContext` обязателен) и физическом разделении хранилищ.
  Живёт в ядре.
- **Авторизация** — решение «этому принципалу можно этот граф для этого действия».
  **Живёт на границе входа. В ядре её нет и быть не должно.**

Размещение: один модуль решения `src/tenancy/authz.py`, вызываемый из каждой точки
входа. Ядро решений не принимает — только получает уже разрешённый `GraphContext`.

```
вход                      кто вызывает authz
─────────────────────────────────────────────────────────
HTTP API                  resolve_graph (src/api/graph_dep.py)
MCP                       верификатор токена при handshake
Intake (заливка, фидеры)  submit() перед записью
Watch (подписка, доставка) при создании подписки и при каждой доставке
Харнесс                   не вызывает — ходит под ключом пользователя
```

Форма: `authorize(principal, graph_id, action) -> allow | deny`, где
`action ∈ {read, write, download_original, admin}`. `download_original` выделен
намеренно — см. §7.

### Модель tenant

Сейчас у графа только `owner TEXT` (свободная строка), у ключа — `owner` и всё.
Добавляется:

```sql
CREATE TABLE IF NOT EXISTS public.tenants (
    id         TEXT PRIMARY KEY,
    name       TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
ALTER TABLE public.graphs    ADD COLUMN IF NOT EXISTS tenant_id TEXT REFERENCES public.tenants(id);
ALTER TABLE public.api_keys  ADD COLUMN IF NOT EXISTS tenant_id TEXT REFERENCES public.tenants(id);
ALTER TABLE public.api_keys  ADD COLUMN IF NOT EXISTS scopes    TEXT[] NOT NULL DEFAULT '{read}';
ALTER TABLE public.api_keys  ADD COLUMN IF NOT EXISTS graph_ids TEXT[];  -- NULL = все графы своего tenant
```

Правило: ключ принадлежит tenant, граф принадлежит tenant, **ключ не адресует граф
чужого tenant даже зная его slug**. Это возвращает отозванную часть D1, но на уровне
tenant, а не перечислением графов в ключе — внутри своего tenant ключ по-прежнему
свободен (`graph_ids IS NULL`), то есть дух амендмента 2026-10-17 сохраняется.

Бутстрап: tenant `default`, в него попадают граф `default` и существующие ключи, включая
`legacy-env`. Без этого legacy-ключи перестанут работать.

**Делать до того, как появятся живые графы у разных клиентов.** Сейчас схема пустая —
миграция бесплатная; потом будет с данными.

## 4. P1 — Intake

Новый код только там, где дыра: дедуп и реестр источников. Остальное — перенос.

### Шаг 1.1 — схема

Правки идут в `src/storage/pg_schema.py` (`GRAPH_DDL`), **не** в `setup_db.py`: эти
таблицы живут в схеме графа. DDL идемпотентный, применяется `migrate_graph_schema`.

Добавить в `documents` (владелец — intake):

```
content_sha256  TEXT        -- sha256 тела
intake_status   TEXT        -- accepted | duplicate | rejected
intake_reason   TEXT        -- причина отказа/дубля, пусто у accepted
duplicate_of    UUID        -- первый документ с тем же хешем
source_kind     TEXT        -- upload | telegram | scraper | …

CREATE UNIQUE INDEX IF NOT EXISTS documents_sha_idx
    ON documents (content_sha256) WHERE content_sha256 IS NOT NULL;
```

**Уникальность автоматически получается в пределах графа** — таблица живёт в схеме
графа. Это и есть причина не выносить индекс хеша в `public`: глобально-уникальный хеш
был бы утечкой (409 на документ чужого tenant раскрывает факт его существования, а хеш
проверяется подбором).

Новая таблица в той же схеме графа (владелец — ядро):

```sql
CREATE TABLE IF NOT EXISTS doc_processing (
    doc_id     UUID PRIMARY KEY REFERENCES documents(id),
    status     TEXT NOT NULL DEFAULT 'pending'
               CHECK (status IN ('pending','processing','completed','vector_only','failed')),
    error      TEXT DEFAULT '',
    summary    TEXT DEFAULT '',
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

`skipped` из домена ядра уходит: это `intake_status='rejected'`, ядро такой документ не
видит. Учесть проверку готовности схемы из Plan B (граф переходит в `ready` только
когда существуют все таблицы `GRAPH_DDL`) — новая таблица должна попасть в тот список.

Критерий: `migrate_graph_schema` прогоняется дважды подряд без ошибок; существующие
строки получают `intake_status='accepted'` и строку в `doc_processing` с текущим
статусом; свежесозданный граф сразу `ready`.

### Шаг 1.2 — дедуп на приёме

sha256 от `contents` (уже в памяти), считается **до** `put_object` — иначе дубль всё
равно съест диск. Политика на коллизию, параметр `on_duplicate` (по умолчанию `reject`):

- `reject` — 409 с `doc_id` первого документа, ничего не пишем;
- `version` — новая строка, `duplicate_of` проставлен, идёт в пайплайн (осознанный
  переингест под новую версию модели);
- `replace` — помечаем старый, заливаем новый (исправление битой заливки).

`force=true` на дубль отображается в `on_duplicate=version`.

Критерий: повторная заливка того же файла в тот же граф даёт 409 и не создаёт объект в
MinIO; заливка того же файла в **другой** граф проходит как новый документ.

Побочный эффект: убирает вторую копию тех же сущностей, которая сегодня гарантированно
порождает лишние пары для ER-судьи (бэклог «ER-судья тратит GPU впустую»).

### Шаг 1.3 — перенос кода в `src/intake/`

Без изменения поведения:

- `src/ingestion/classifier.py` → `src/intake/classifier.py` (вердикт — решение приёма);
- `src/ingest_queue/*` → `src/intake/queue/`;
- `src/api/routes/ingest.py` → `src/intake/api/ingest.py`;
- `src/api/routes/documents.py` → `src/intake/api/documents.py`;
- SQL по `documents` из `src/storage/postgres.py` → `src/intake/repository.py`;
  в `storage/postgres.py` остаётся `doc_processing`. Обращение из
  `workflow/graph_lifecycle/activities.py` (удаление графа) переводится на репозиторий
  intake.

Классификатор **остаётся исполняться в воркере** (LLM-гейт нельзя держать синхронно в
HTTP-запросе), но пишет вердикт в `intake_status`, а не в статус обработки. Процесс не
делим — делим владение.

Критерий: ядро (`src/graph`, `src/workflow` кроме активности-классификатора,
`src/retrieval`) не импортирует `src/intake`, кроме `doc_id` и пути. Проверяется
arch-тестом на импорты.

### Шаг 1.4 — реестр источников и принципалы фидеров

Фидеры (`tg_ingest`, будущий скрейпер статистики) регистрируются как источники:
`source_kind`, политика дубля по умолчанию, граф, группа, приоритет. Интерфейс —
`submit(blob, meta) -> IntakeVerdict`, HTTP — тот же `/ingest`.

Под tenant: ключ фидера получает `scopes={write}` и фиксированный граф. **Ключ фидера не
должен уметь читать** — сегодня такого различения нет вовсе.

Критерий: `tg_ingest.py` ходит через ту же точку, что и ручная заливка, получает
осмысленный отказ на дубль; его ключом нельзя выполнить поиск.

### Шаг 1.5 — читаемая статистика приёма

Закрывает «Backlog: Documents Stats Endpoint»: `GET /intake/stats` — by_status,
throughput, stuck, coverage, errors, доля дублей. Разрез по графу, не сквозной.

Критерий: по ответу видно, почему документов в графе меньше, чем залито.

### Шаг 1.6 — квоты (отложено, но место зафиксировать)

Честность приёма между tenant живёт здесь. В спеке мультиграфа per-graph fairness явно
в backlog; колонка `graphs.max_inflight` уже заведена и не используется — **не удалять**.

## 5. P2 — Наблюдение и уведомления

Строго после P1: событие «новая сущность» без провенанса приёма («из какого источника,
не дубль ли документ») — полуфабрикат.

1. Вынести `watch_journal.py` + `workflow/monitor/*` + MCP-инструменты в `src/watch/`.
   Таблицы уже в схеме графа, мигрировать нечего.
2. **Политика событий** — чего нет: что считается новым (первое упоминание вообще против
   первого в этом источнике), окно подавления повторов, порог значимости.
3. **Каналы доставки** поверх `post_alert`: Telegram, дайджест по расписанию,
   подтверждение прочтения (`watch_seen` есть). Ретраи и дедуп доставки.
4. Провенанс в теле события: источник, дата документа, дубль/оригинал.
5. **Доставка — точка утечки.** URL назначается владельцем подписки, а тело несёт имена
   сущностей графа. Проверять право на граф **и при создании подписки, и при каждой
   доставке** — права могли отозвать после подписки. Физическая изоляция таблиц от этого
   не спасает: утечка идёт наружу, через webhook.

Критерий: подписка даёт одно уведомление на событие, а не одно на документ; в нём видно,
откуда оно; отзыв прав останавливает доставку.

## 6. P3 — Харнесс

Последним: иначе привяжется к интерфейсам, которые P1/P2 ещё перепишут.

Контракт — три группы инструментов, по контуру на группу:

- **intake**: залить, проверить дубль, статус приёма, достать оригинал;
- **знание** (есть): поиск, граф, аналитика, вики;
- **наблюдение**: подписаться, лента, подтвердить.

Два правила, без которых tenant бессмыслен:

1. **Агент работает от имени пользователя, а не своим ключом.** Харнесс с собственным
   ключом на все графы обнуляет изоляцию одним промптом. Нужен проброс принципала:
   ключ пользователя → MCP-соединение → `GraphContext`.
2. **Граф не параметр инструмента. Никогда.** В спеке это уже так (D4: граф привязан к
   соединению) — именно на это свойство опирается работа от имени пользователя. Если
   граф станет аргументом, модель его подберёт.

Открытый вопрос: **что такое dsh** — следа в проекте нет. По Hermes трек размечен
(подход A: MCP-SSE + skill knowledge-base + починка SSE-аутентификации), его и берём за
основу, пока не уточнено.

## 7. Кто отдаёт исходный документ

**Intake, и это самая строгая точка контура.**

Сегодня `GET /documents/{id}?variant=original|text`
(`src/api/routes/documents.py`): зависит от `resolve_graph`, читает `documents` из схемы
графа, ключ MinIO графо-префиксный. Изоляция обеспечена.

Что следует для плана:

1. Маршрут уезжает в `src/intake/api/documents.py` вместе с владением реестром. Ядро
   файлы не отдаёт вообще.
2. **Отдельное право `download_original`.** Поиск отдаёт обработанные фрагменты; этот
   маршрут отдаёт исходный бинарник целиком — персональные данные, метаданные файла, всё,
   что не попало в граф. Право на поиск не должно автоматически давать право на выгрузку.
   Для корпуса уголовных дел это не формальность.
3. **Журнал выдач**: кто, какой документ, какой вариант, когда. Без него не ответить на
   «что утекло» при компрометации ключа.
4. **Легаси-ветка чтения с диска** (`if not path.startswith("s3://")` → `FileResponse`)
   читает произвольный локальный путь из колонки БД. Источник пути серверный, дыры
   сейчас нет, но под мультитенантностью ветку убрать или ограничить белым списком.
   Перед переносом проверить, остались ли вообще строки без `s3://`.
5. Прямой доступ к MinIO мимо маршрута закрыть: бакет не публичный, presigned-ссылки —
   только короткоживущие и только из intake после проверки права.

Пункты 1–3 входят в шаг 1.3, пункт 4 — проверка перед переносом, пункт 5 — задача
деплоя.

## 8. Риски

- **58 коммитов мультиграфа не запушены и, судя по всему, не выкачены.** Пока они живут
  только локально, любая работа поверх них — на одном диске. Это главный риск плана, и он
  операционный, а не архитектурный.
- **Миграция `documents`** — единственное место, где можно сломать живое. Смягчение: SQL
  узкий (3 файла), миграция аддитивная, старые колонки не удаляются до перевода читателей.
- **Классификатор fail-soft**: сомнение трактуется как «брать». Под владением intake
  возникнет соблазн сделать его строгим — не делать, цена ложного отказа выше.
- **Точный хеш не ловит «тот же документ в другом формате»** (docx → txt, пересохранённый
  PDF). Осознанно вне объёма: нечёткий дедуп — отдельная задача, сперва точный.
- **Переезд `/documents/{id}`** ломает клиентов. Проверить Lens и бота; при сомнении
  оставить старый путь редиректом.
- **Бутстрап tenant для legacy-ключей**: пропустить = разом отключить всех, кто ходит по
  `API_KEYS` из env.

## 6a. Состояние P3 на 2026-10-20 (решение пользователя)

**P3 отложен, и это решение, а не недоработка.** P1 и P2 закрыты —
контракты, на которые должен опираться харнесс, стабилизированы: приём
отвечает `/ingest` + `/intake/stats` + выдача оригинала с журналом,
наблюдение отвечает подпиской, лентой и доставкой с провенансом.

Чего P3 ждёт: **выбора харнесса**. Открытый вопрос §10.2 («что такое
dsh») остаётся открытым; размеченный трек есть только по Hermes (подход
A: MCP-SSE + skill `knowledge-base` + починка SSE-аутентификации,
`docs/runbook/hermes.md`). Второй живой кандидат — openclaw на .31
(`@kb_llamaindex_bot`), он уже ходит в KB своим ключом.

Что разблокирует работу: названный харнесс. После этого P3 — три группы
инструментов (приём / знание / наблюдение) плюс ДВА правила, без которых
арендаторы бессмысленны: агент работает от имени пользователя, а не
своим ключом, и граф не параметр инструмента (он привязан к соединению,
D4 спеки мультиграфа).

Готовое к моменту выбора: шов MCP уже выбирает граф тем же правилом, что
HTTP (`choose_graph_id`), и уже авторизует действие — то есть проброс
принципала упирается в харнесс, а не в ядро.

## 9. Порядок

`P0 → P1 → P2 → P3`, модель tenant (§2) — до появления живых графов у разных клиентов,
то есть практически вместе с P0.

Ранее план требовал сперва влить ветку `a-tsitanov/tenant` — **сделано 2026-10-18**,
пункт снят.

Объём: P0 — часы; P1 — основной кусок (шаги 1.1–1.3 обязательны, 1.4–1.6 можно
отложить); P2 — код написан, нужна политика и каналы; P3 — после стабилизации контрактов.

Каждому из P1, P2, P3 нужен свой цикл «спека → план → реализация». Этот документ — карта,
не спека.
