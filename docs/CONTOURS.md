# Контуры, слои и потоки данных

Как устроено приложение: шесть слоёв, три контура, четыре процесса,
19 таблиц в схеме графа и 5 общих. Этот документ — текстовый источник
истины; визуальная версия того же — артефакт
<https://claude.ai/artifact/CC7fm7Mp1DePjHrWbnqanB> (приватный).

## 1. Слои

Зависимости идут только вниз. Слой 2 решает «можно ли», слой 3 — «что
делать», слои 5–6 не решают ничего: они получают уже разрешённый
`GraphContext`.

| № | Слой | Что в нём |
|---|---|---|
| 1 | Клиенты — вне приложения | фидеры, web UI, агент через MCP, оператор со скриптами. У каждого свой ключ |
| 2 | Вход и доступ | маршруты FastAPI, три mcp-сервера, шов: ключ → выбор графа → `authz.guard(действие)` → `GraphContext` |
| 3 | Прикладной слой | три контура: приём (`src/intake`), ядро (`src/workflow`, `src/graph`, `src/retrieval`, `src/analytics`), наблюдение (`src/watch`) |
| 4 | Оркестрация и транспорт | Temporal (воркфлоу, 9 пулов), RabbitMQ (N очередей приёма), `ingest-consumer` с prefetch = K |
| 5 | Адаптеры хранения | `src/storage` (пул Postgres, `search_path` на схему графа, DDL, MinIO, чанки), сессия Nebula, индекс Milvus, клиент LiteLLM |
| 6 | Хранилища | Postgres (`g_<id>` + `public`), NebulaGraph (пространство), Milvus (три коллекции), MinIO (префикс), LiteLLM снаружи |

**Контур — это пакет и его таблицы, а не процесс.** Один и тот же
`worker` держит шаги ядра, два файла-адаптера приёма и активности
наблюдения; границы существуют на уровне импортов и владения таблицами.

## 2. Правила зависимостей

Исполняются arch-тестами по AST (`tests/test_intake/test_boundaries.py`,
`tests/test_watch/test_boundaries.py`) — ленивый импорт внутри функции
тоже виден. Каждое исключение названо файлом, и список падает, если файла
нет.

| Направление | Можно | Чем держится |
|---|---|---|
| сверху вниз по слоям | да | обычный импорт |
| снизу вверх | нет | контуры не знают о маршрутах и инструментах; по соглашению, тестом не закреплено |
| ядро → приём | два файла | `src/workflow/activities/classify_document.py`, `src/workflow/activities/mark_skipped.py` — гейт исполняет воркер, решение принадлежит приёму |
| ядро → наблюдение | три файла | `src/workflow/worker.py` (регистрация активностей), `src/workflow/activities/build_property_graph.py` (запись журналов), `src/graph/entity_resolution.py` (переписывание vid при слиянии) |
| наблюдение → приём | только реестр | один вопрос «что это за документ» — `IntakeRepository.provenance_of`, пачкой |
| приём → ядро | нет | `src/intake` не импортирует `src.graph` вовсе |
| приём → таблица ядра | да, одно чтение | квота считает `doc_processing`; это SQL, не код, владение статусом остаётся у ядра |
| кто угодно → `src/storage` | да | он ниже обоих контуров |
| запись в бакет загрузок | только приём | ядро получает `doc_id` и ссылку, а не право создать тело |

## 3. Контроль на входе

Ни одну проверку не делает клиент. Фидер умеет только не присылать
дважды то, что уже прислал, — и даже если он сбился, его остановит дедуп.

| Проверка | Слой | Когда | Отказ |
|---|---|---|---|
| форма: группа, очередь, приоритет | вход | до любой работы | 422 |
| право: ключ × граф × действие | доступ | до чтения тела | 403 своё без права, 404 чужое или неизвестное |
| повтор тела по sha256 | приём | до хранилища | 409, объект не создаётся |
| квота графа (`graphs.max_inflight`) | приём | после дедупа, до хранилища | 429 + `Retry-After` |
| это документ или мусор | приём, исполняет воркер | после заливки — гейту нужна модель | `intake_status='rejected'`, наружу виден как `skipped` |

Две оговорки про классификатор: он **выключен по умолчанию**
(`CLASSIFIER_ENABLED=false`), то есть смысловой фильтрации может не быть
вовсе; и он fail-soft — сомнение означает «брать», потому что цена
ложного отказа выше цены лишнего документа.

## 4. Процессы

| Процесс | Команда | Что делает |
|---|---|---|
| `api` | `uvicorn src.api.main:app` | маршруты приёма, выдачи, поиска, отчётности, админки; шов авторизации |
| `worker` | `python -m src.workflow.worker` | 9 пулов, по процессу на пул (`WORKER_GROUPS` выбирает, какие поднять) |
| `ingest-consumer` | `python -m src.intake.queue.consumer` | читает очереди приёма с prefetch = K и стартует воркфлоу документа |
| `mcp-search` / `mcp-tools` / `mcp-stats` | `python -m src.mcp.*_server` | инструменты агента; граф привязан к соединению, параметром инструмента не бывает |

### Пулы воркера

| Пул | Очередь | Что крутится | Зачем отдельно |
|---|---|---|---|
| `main` | `kb-ingest` | `DocumentIngestWorkflow`; источник, классификатор, парсинг, векторы, финализация, пометки | дешёвые шаги документа, их много |
| `llm` | `kb-ingest-llm` | извлечение графа из текста | свой лимит под модель; пул и есть единственный дроссель |
| `merge` | `kb-ingest-merge` | `GraphBuildWorkflow`, слияние с ER, запись графа | самое тяжёлое по блокировкам |
| `search` | `kb-search-small` | шесть воркфлоу поиска плюс шаги аналитики | чтение не должно ждать ингеста |
| `large` | `kb-search-large` | синтез ответа, тяжёлая аналитика | длинный контекст, свой лимит |
| `graph_build` | `kb-graph-build` | сообщества, материализация, создание и удаление графа | офлайн-работа |
| `wiki` | `kb-wiki` | свип редактора статей | пишет статьи, трогает граф |
| `scheduler` | `kb-ingest-scheduler` | синглтон допуска (ветка `temporal`) | история синглтона не должна висеть на общем пуле |
| `monitor` | `kb-monitor` | `MonitorSweepWorkflow`: свип, затем доставка | ходит в чужие адреса — свой таймаут и ретраи |

Шаги жизненного цикла графа планируются на отдельную очередь
`kb-graph-lifecycle` (боковые воркеры): иначе создание графа стояло бы в
очереди за его же наполнением.

## 5. Путь документа

| Шаг | Что читает и пишет | Отказ |
|---|---|---|
| 1. `POST /api/v1/ingest` | `public.api_keys` по хешу ключа, кеш процесса 30 с; нет строки → ключи из env | 401 |
| 2. выбор графа | `public.graphs` → `GraphContext` (схема, пространство, коллекции, префикс, арендатор, квота) | 404 чужой, 409 не `ready` |
| 3. `authz.guard(write)` | таблиц не трогает: решение по ключу и арендатору графа | 403 / 404 |
| 4. sha256 тела, поиск владельца | `documents` по `content_sha256` (частичный уникальный индекс) | 409 дубль, 422 `replace` |
| 5. квота | счёт незавершённых в `doc_processing` | 429 + `Retry-After` |
| 6. заливка | MinIO `kb-uploads`, ключ `<префикс графа>/<doc_id>/<имя файла>` | 503 хранилище |
| 7. транзакция приёма | `documents` + `doc_processing` одним commit | гонка по индексу → уборка префикса, 409 |
| 8. очередь | RabbitMQ `ingest.*` с приоритетом, либо сигнал синглтону | — |

Ответ `202 {"job_id": <doc_id>}`. Статус — `GET /api/v1/ingest/{job_id}`
(право `read`), оригинал — `GET /api/v1/documents/{doc_id}` (право
`download_original`, каждая выдача пишется в журнал).

### Повтор тела

| Случай | `documents` | `doc_processing` | MinIO | Ответ |
|---|---|---|---|---|
| новое тело | строка, хеш заполнен | строка `pending` | новый объект | 202 |
| повтор, политика `reject`, есть канал или группа | строка-наблюдение: `intake_status='duplicate'`, `duplicate_of`, хеш NULL | нет и не будет | тот же объект | 409 |
| повтор без канала и группы | ничего | — | ничего | 409 |
| повтор, политика `version` | новая строка, `duplicate_of`, хеш NULL | строка `pending` | новый объект | 202 |
| квота исчерпана | ничего | — | ничего | 429 |

Хеш принадлежит канонической строке: и у версии, и у наблюдения
`content_sha256` пишется NULL, поэтому в частичный уникальный индекс
входит только владелец тела. Без этого удаление канонического документа
с двумя версиями падало бы — внешний ключ обнулил бы ссылки одним
UPDATE, и версии одновременно вошли бы в индекс с одинаковым хешем.

## 6. Фидер

Базового класса нет и роли такой в коде нет: фидер — любой внешний
клиент, который делает multipart-POST своим ключом. Живых три:
`scripts/tg_ingest.py`, `deploy/offline/loadtest/loader.py`,
`scripts/ingest_medical.py`. «Регистрация фидера» — это выпуск ключа
(`scripts/tenant_admin.py`), а не строка в таблице: `owner` ключа
становится `documents.source_kind`, единственный `graph_ids` — графом по
умолчанию для этого ключа.

| Забота | Чья | Чем держится |
|---|---|---|
| не прислать то же сообщение второй раз | фидер | `last_id` на диалог в файле состояния, пишется после каждого сообщения |
| не завести второй документ на то же тело | приём | sha256 в пределах графа |
| сохранить канал у перепоста | приём | строка-наблюдение со ссылкой на владельца тела |
| не свалить на пайплайн больше, чем он берёт | приём | квота графа → 429 |
| атрибуция «кто принёс» | ключ | `documents.source_kind` = `owner` ключа |
| в какой граф писать | ключ | единственный `graph_ids` — граф по умолчанию |

Поведение `tg_ingest` на ответы приёма:

| Ответ | Фидер | Курсор |
|---|---|---|
| 202 | `sent` | двигается |
| 409 | `duplicate` — для прохода это успех | двигается: повтор ничего не изменит |
| 429 | ждёт `Retry-After`, до 3 попыток, ожидание ≤ 60 с, потом `failed` | НЕ двигается, раунд обрывается |
| 5xx, сеть | `failed` сразу | НЕ двигается |
| пустое сообщение | `skipped`, запрос не отправляется | двигается |

Чего фидер не умеет: правка сообщения (id ниже курсора — изменённый текст
не придёт) и удаление в источнике (документ в графе остаётся). Потеря
файла состояния безопасна: канал перечитывается с нуля, на каждое
сообщение приходит 409, второй копии не появляется.

## 7. Обработка в воркере

`fetch_source` → классификатор → `parse_and_chunk` (staging-бакет) →
векторы в Milvus → извлечение → слияние с ER (`er_verdict`, вектор
сущностей) → запись графа (Nebula, `entity`, `entity_alias`) + журналы
наблюдения (`entity_mention`, `edge_new`) → `finalize`
(`doc_processing`, `ingest_metrics`).

Отказ классификатора строку обработки **удаляет**, а не переводит в
терминальный статус: домен `doc_processing` намеренно без `skipped`.
Наружу такой документ виден как `skipped` — это считает выражение
эффективного статуса, а не колонка.

### Эффективный статус

| Состояние строк | Что отдаёт эффективный статус | Почему |
|---|---|---|
| есть строка обработки | её статус | обработка идёт или кончилась |
| `intake_status='rejected'` | `skipped` | отказ приёма; строки обработки нет |
| `intake_status='duplicate'` | `duplicate` | наблюдение перепоста; обработки не было и не будет |
| ни того, ни другого | `documents.status` | дорасщеплённые строки, которые не трогали |

Три поверхности отчётности: `GET /api/v1/intake/stats` (лестница сверки
«залито против принято», срез графовый), `GET /api/v1/stats/messages` и
`/stats/timeline` (срез по каналам и группам, строки с пустым каналом
отброшены), `python -m scripts.check_ingestion` (прямо из Postgres, «что
лежит в базе»). Первые две обязаны сходиться между собой при заполненном
канале, третья — нет, у неё другой вопрос.

## 8. Наблюдение

Журналы ингеста → курсор на журнал (`monitor_cursor`, выдержка 60 с на
строку) → детекторы → провенанс приёма пачкой → `watch_event` (вставка с
дедупом по ключу). Отдельно рост риска: Nebula отдаёт текущее и прежнее
значение по vid подписок, журнала у него нет.

Два выхода из одной таблицы событий:

| Выход | Что читает и пишет |
|---|---|
| лента (pull) | `watch_event` × `watch` × `watch_seen`, путь документа из реестра приёма; подтверждение пишет `watch_seen` |
| доставка (push) | `watch.created_by` → `public.api_keys` по владельцу → право `read` на граф; `watch_delivery` (PK «владелец + событие» = дедуп), сверх потолка — `watch_digest` одной сводкой |

«Отправлено» и «прочитано» — разные факты и разные таблицы.
`AUTHZ_MODE` на доставку не влияет намеренно: «пропустить» здесь значит
отправить содержимое графа наружу, а откатить это нельзя.

## 9. Реестр таблиц

Схема графа — `public` для графа `default` и `g_<id>` для остальных;
`search_path` не падает обратно в `public`, поэтому забытая таблица даёт
ошибку, а не чужие данные.

| Таблица | Контур | Пишет | Чем держится |
|---|---|---|---|
| `documents` | приём | маршрут приёма, запись вердикта классификатора | частичный уникальный индекс по `content_sha256` |
| `doc_processing` | ядро | финализация, пометка сбоя, приём при вставке | внешний ключ на `documents` с каскадом; домен без `skipped` |
| `document_download` | приём | выдача оригинала, перед отдачей байт | внешнего ключа НЕТ: журнал переживает удаление документа |
| `ingest_metrics` | ядро | финализация | по строке на прогон воркфлоу |
| `fact_supersede` | ядро | слияние с ER | граф хранит победившее утверждение, здесь — проигравшее |
| `entity` | ядро | запись графа, бэкфилы | триграммные индексы по нормализованному имени |
| `entity_alias` | ядро | разрешение сущностей | ключ «алиас + канонический vid» |
| `er_verdict` | ядро | судья ER | кеш решённых пар; экономит GPU |
| `stat_indicator`, `stat_observation` | ядро | загрузка статистики | индексы по смыслу показателя и периоду |
| `watch` | наблюдение | MCP-инструменты подписки | одна подписка на «владелец + сущность» |
| `entity_mention` | наблюдение | ядро на записи графа | ключ «сущность + документ», отдельный id под курсор |
| `edge_new` | наблюдение | ядро на записи графа | уникальность по паре: связь фиксируется один раз навсегда |
| `watch_event` | наблюдение | свип | `dedup_key` уникален; одна строка на событие, не на подписчика |
| `watch_seen` | наблюдение | лента и подтверждение | ключ «владелец + событие» |
| `watch_delivery` | наблюдение | доставка | PK «владелец + событие» И ЕСТЬ дедуп отправки |
| `watch_digest` | наблюдение | доставка при переполнении потолка | своя таблица: сводок много, по одной за проход |
| `monitor_cursor` | наблюдение | свип, в одной транзакции с событиями | позиция на журнал; двигается и без подписок |
| `risk_snapshot` | — | никто | мёртвая: прежний риск лежит на узле графа |

Общие в `public`:

| Таблица | Зачем | Кто читает на горячем пути |
|---|---|---|
| `graphs` | физические имена, статус, арендатор, `generation`, квота | каждый запрос через кеш реестра 30 с |
| `api_keys` | хеш, владелец, арендатор, `scopes`, `graph_ids` | каждый запрос по хешу (кеш 30 с); доставка — по владельцу, без кеша |
| `tenants` | арендаторы; ключ и граф принадлежат одному | администрирование |
| `schema_migration` | маркеры одноразовых шагов (расщепление записи посхемно, выдача прав легаси-ключам) | `scripts/setup_db.py` |
| `bot_user`, `bot_request` | остаток удалённого Telegram-бота: данные есть, кода нет | никто |

## 10. Инварианты, которые легко сломать молча

- **Статус.** SQL по реестру приёма, называющий статус или ошибку, обязан
  джойнить `doc_processing`. Иначе он не падает и не ругается — он
  показывает дорасщеплённое значение, у новых строк вечное `pending`.
- **Хеш.** Уникальность — строго в пределах схемы графа. Глобальный
  индекс был бы утечкой между арендаторами: 409 на чужое тело раскрывает
  факт его существования, а хеш проверяется подбором.
- **Владелец подписки.** `watch.owner` — корзина ленты и сегодня это
  константа. Право на доставку проверяется по `watch.created_by` — имени
  ключа, которым подписались; пусто значит «только лента».
- **`GraphContext`.** Функции, трогающие хранилище, принимают его явным
  аргументом. Забытый граф — ошибка типов, а не тихая запись в `default`.
- **Бакет.** В бакет загрузок пишет только приём. Ядро получает `doc_id`
  и ссылку на содержимое, а не право его создать.
